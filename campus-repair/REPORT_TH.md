## หลักการและเหตุผล

เมื่ออุปกรณ์คอมพิวเตอร์ในสถานศึกษาเสีย การแจ้งด้วยวาจาหรือข้อความหลายช่องทางอาจทำให้ข้อมูลไม่ครบ
และผู้แจ้งไม่ทราบความคืบหน้า โครงงานนี้จึงรวมการแจ้งและติดตามงานไว้ในเว็บไซต์เดียว
ผู้ดูแลเห็นรายการทั้งหมด ส่วนผู้ใช้เห็นเฉพาะรายการของตน เพื่อลดการเปิดเผยข้อมูลติดต่อ

## วัตถุประสงค์

1. รับข้อมูลอุปกรณ์ สถานที่ อาการเสีย และข้อมูลติดต่ออย่างเป็นระบบ
2. ให้ผู้ดูแลค้นหาและบันทึกผลการซ่อมพร้อมสถานะ
3. ให้ผู้แจ้งติดตามความคืบหน้าและประวัติได้ด้วยตนเอง
4. ฝึกใช้ Python, Flask, SQLite, HTML/CSS และการตรวจสิทธิ์ในเว็บแอป

## ขอบเขตและเทคโนโลยี

ใช้ Python Flask สำหรับจัดการคำขอ, SQLite สำหรับข้อมูล, Jinja สำหรับสร้าง HTML,
Bootstrap และ CSS สำหรับหน้าจอ responsive และ Flask-WTF สำหรับ CSRF
แบ่ง User และ Admin ไม่รวมระบบยืมคืน อีเมล การชำระเงิน หรือ API ภายนอก

รุ่นสำหรับ deploy ใช้ GitHub เก็บโค้ด, Vercel รัน Flask และ PostgreSQL ภายนอกเก็บข้อมูลถาวร
ยังคง SQLite สำหรับการเรียนและรันในเครื่อง โดยเลือกผ่าน environment `DATABASE_URL`
เพิ่ม `database.py` เป็น adapter ขนาดเล็ก ไม่เปลี่ยนหน้าเว็บหรือใช้ frontend framework
ฐานข้อมูลออนไลน์เริ่มต้นใหม่ ไม่ย้ายรายการจาก SQLite อัตโนมัติ

## การออกแบบฐานข้อมูล

| ตาราง | คีย์ / ข้อมูลสำคัญ | หน้าที่ |
| --- | --- | --- |
| users | id (PK), username (unique), name, password_hash, role, created_at | บัญชีและบทบาท |
| repairs | id (PK), user_id (FK), equipment, room, description, contact, status, เวลา | รายการแจ้งซ่อม |
| repair_history | id (PK), repair_id (FK), actor_id (FK), status, note, created_at | ประวัติและผู้บันทึก |

ความสัมพันธ์: users 1 → หลาย repairs; repairs 1 → หลาย repair_history;
users 1 → หลาย repair_history ในฐานะผู้บันทึก
ฐานข้อมูลมี CHECK ควบคุม role/status และเปิด foreign keys ทุก connection

## การทำงานของระบบ

ผู้ใช้สมัครและเข้าสู่ระบบ จากนั้นกรอกแบบฟอร์มแจ้งซ่อม Flask ตรวจข้อมูลก่อนเพิ่มรายการสถานะรอรับเรื่อง
พร้อมประวัติเริ่มต้น ผู้ดูแลเข้าสู่ระบบเพื่อดูภาพรวม ค้นหา และอัปเดตสถานะพร้อมบันทึก
ระบบเปลี่ยนสถานะและเพิ่มประวัติใน transaction เดียว ผู้ใช้เปิดรายละเอียดเพื่ออ่านผลล่าสุด
ผู้ดูแลสามารถย้อนสถานะเมื่อต้องซ่อมซ้ำ แต่ต้องบันทึกเหตุผลไว้

## การรักษาความปลอดภัย

เก็บรหัสผ่านแบบ hash; สร้าง admin ผ่าน CLI โดยไม่ฝังรหัสผ่านจริง;
ตรวจสิทธิ์ที่ server และตรวจเจ้าของรายการทุกครั้ง; ทุก POST ตรวจ CSRF;
ใช้ parameterized SQL และ Jinja autoescape; ตรวจความยาวและค่าที่อนุญาตใน Python
เก็บ secret สุ่มในไฟล์ที่ไม่ส่งไปกับโปรเจกต์

## ผลการทดสอบ

การทดสอบอัตโนมัติครอบคลุม flow ของทั้งสองบทบาทและกรณีสิทธิ์ไม่ถูกต้อง
รันชุดทดสอบกับทั้ง SQLite และ PostgreSQL จริง รวมกรณี transaction ล้มเหลวต้อง rollback
ดูผลที่รันจริงใน `TEST_RESULTS_TH.md` และขั้นตอนทดสอบซ้ำใน README
ผลที่คาดหวังคือ User B ไม่เห็นรายการของ User A, User เปลี่ยนสถานะไม่ได้,
Admin เปลี่ยนสถานะและบันทึกได้ และ User เห็นประวัติการเปลี่ยนแปลงครบถ้วน

## ประโยชน์และข้อจำกัด

ช่วยรวมข้อมูลและเพิ่มความชัดเจนในการติดตามงาน ใช้เทคโนโลยีไม่ซับซ้อน จึงเหมาะกับการเรียน
รุ่นนี้ยังไม่มีแจ้งเตือน ไฟล์รูป หรือระบบจำกัดความถี่ login และใช้ development server สำหรับสาธิต
การใช้งานจริงควรเพิ่ม HTTPS, rate limiting, backup และ production server

## แนวทางสาธิตและตอบคำถาม

1. เปิดเว็บ สมัคร User และแจ้งซ่อมหนึ่งรายการ
2. Login Admin อธิบาย dashboard แล้วเปลี่ยนเป็นกำลังดำเนินการและเสร็จสิ้นพร้อมบันทึก
3. Login User อีกครั้งเพื่อแสดงประวัติและทดลองผู้ใช้คนอื่นที่เข้าถึงรายการนี้ไม่ได้
4. เปิด `schema.sql` อธิบาย primary key, foreign key และความสัมพันธ์
5. เปิด `app.py` อธิบายเส้นทาง request → ตรวจสิทธิ์ → ตรวจข้อมูล → SQL → render/redirect

**ทำไมเลือก Flask?** มี routes ชัดเจนและใช้ Python ตรงไปตรงมา เหมาะกับโปรเจกต์ขนาดเล็ก

**ทำไมเลือก SQLite?** เป็นไฟล์เดียว ไม่ต้องติดตั้ง database server แต่ไม่เหมาะกับการเขียนพร้อมกันจำนวนมาก

**ทำไมต้อง history แยก?** ฟิลด์ status เก็บค่าปัจจุบัน ส่วน history เก็บแต่ละเหตุการณ์โดยไม่ทับบันทึกเก่า

**ทำไมตรวจสิทธิ์ใน server?** ผู้ใช้แก้ URL หรือส่ง POST เองได้ การซ่อนปุ่มอย่างเดียวจึงไม่พอ

**CSRF ต่างจากตรวจ role อย่างไร?** CSRF ตรวจว่าคำขอแบบฟอร์มมี token ของ session;
role ตรวจว่าบัญชีมีสิทธิ์ทำงานนั้น ต้องใช้ทั้งสองอย่าง

**หมายเหตุ:** เติมข้อมูลผู้จัดทำ ปรับรายงานตามแบบของอาจารย์ และศึกษารหัสพร้อมทดลองแก้ไขก่อนนำเสนอ
